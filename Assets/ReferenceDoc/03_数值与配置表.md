# 03 数值与配置表

> 本文档是**配置表的唯一数据源（初版 v1.1）**。开发时可直接转成 Excel / CSV，再由导表工具生成二进制或 JSON。
> 所有数值为**初版**，M2 阶段通过自测脚本与试玩校准；改数值只改表，不改代码。
> 时间单位：秒（s）。价格单位：金币（G）、钻石（D）、抽卡券（T）。
>
> **v1.1**：配置表改由 **Luban** 导出（见第 13 节与 `04_技术方案与架构.md` §5.4）。各章节中的 `Cxx / RCxxx / Fxx / Pxx / Axxx` 为**可读编码（`code`）**，配置表主键统一为 **int `id`**（取编码数字部分，如 `C01→1`、`RC009→9`、`F03→3`、`P02→2`、`A001→1`）。

## 8. OrderRule（订单规则与奖励）

### 8.1 生成参数

| 参数 | 值 |
|---|---|
| 每日订单数 | 6 |
| 难度档（需求项数） | 简单 1 项 / 普通 2 项 / 困难 3 项，比例 3 : 2 : 1 |
| 原料 / 加工品权重 | Lv1~3：60% / 40%；Lv4 起：40% / 60% |
| 原料数量范围 | 2~6（价值越高数量越少：sell ≥ 30 时 2~3） |
| 加工品数量范围 | 1~3（sell ≥ 130 时 1~2） |
| 可立即完成的订单 | （原文易歧义，见下方 **M2 澄清（T002）**；实现与验收不得把“可生产”写成“可提交通过”） |
| 候选物品池 | 玩家已解锁的作物产出、采集物（不含稀有掉落）、已解锁配方产物 |

#### M2 澄清（T002，2026-10-21）

原“可立即完成 = 持有 **或** 可由已解锁配方/作物制作”与总计划测试“至少 2 条可立即完成”在空背包下不可同时成立。M2 冻结为分情形语义（权威决策见 [M2_ADR_T002](M2_ADR_T002_写命令与玩法决策冻结.md) D05）：

| 术语 | 定义 |
|---|---|
| 真正可提交 | 当前库存可满足该订单全部需求 |
| 已解锁可生产 | 不依赖当前库存；需求均可由已解锁作物播种收获或已解锁配方加工的有限链获得 |
| 空候选 | 解锁集合下候选池为空 |

| 情形 | 输入示例 | 边界 | 预期（规格；算法未实现前不得标通过） |
|---|---|---|---|
| 库存充足 | 背包物品足以覆盖 ≥2 条候选订单需求 | 对保证的 2 条做**合并库存分配**（两条同时可交） | 日订单中 ≥2 条真正可提交 |
| 库存不足 | 空背包或原料不足以交单，但作物/配方链非空 | 禁止灌礼包/零需求单凑数 | ≥2 条已解锁可生产，并显式降级原因；不保证真正可提交 |
| 空候选 | 解锁为空或过滤后池空 | 不得静默成功空列表 | 生成明确失败 |

经济数值（难度比例、数量范围、奖励公式、每日 3/6 奖）仍以上表与 §8.2–8.3 为准，本澄清不改任何数字。

### 8.2 奖励公式

设订单需求物品总价值 `V = Σ(sellPrice × count)`（`sellPrice` 以 Item 表为准）。

| 项 | 公式 |
|---|---|
| 金币 | `round(V × k)`，k：简单 1.3 / 普通 1.4 / 困难 1.6 |
| 经验 | `max(5, round(V × 0.25))` |
| 稀有加成 | 10% 概率，金币 ×1.5 |

**舍入约定（权威，不改系数）**：文中 `round` 表示**远离零的中点舍入**（正数即常见四舍五入；等价 .NET `MidpointRounding.AwayFromZero`）。系数 k 与 0.25 保持上表，不得为凑整数暗改。

**示例（用于校验；V 由源表价重算）**

| 订单 | 源表价核对 | V | 难度 | 金币（公式） | 经验（公式） |
|---|---|---|---|---|---|
| 小麦 ×6 | 8×6 | 48 | 简单 | 48×1.3=62.4→**62** | 48×0.25=12→**12** |
| 面包 ×2 | 90×2 | 180 | 简单 | 180×1.3=**234** | 180×0.25=**45** |
| 蔬菜汤 ×1、番茄酱 ×1、花束 ×2 | 80+85+45×2 | 255 | 困难 | 255×1.6=**408** | 255×0.25=63.75→**64** |
| 草莓蛋糕 ×2、南瓜派 ×1、玉米饼 ×1 | 260×2+190+130 | 840 | 困难 | 840×1.6=**1344** | 840×0.25=**210** |

**勘误（2026-10-21 T002 审查）**：旧表示例曾写「面包 ×2 / 简单 / 金币 252」。252=180×1.4（普通档），与简单档 k=1.3 及源表价矛盾。以公式与 Item.sell 为准更正为 **234**；**未改**任何经济系数或售价。

> 订单金币高于直接出售约 30%~60%，订单是主要收入来源之一；出售保留作为“清库存”手段。

### 8.3 每日奖励汇总

| 条件 | 奖励 |
|---|---|
| 完成 3 条 | 抽卡券 ×1（`PlayerInfo.ticket`，**不占背包格**） |
| 完成 6 条 | 抽卡券 ×1，钻石 ×20（均为货币字段，**不占背包格**） |

### 11.4 概率验证（脚本模拟结果）

模型：SSR 按“基础 1% + 40 抽起每抽 +4% + 60 抽硬保底”，SR 按“基础 6% + 每 10 抽保底”，不含 UP 逻辑；200000 次抽取的蒙特卡洛 + 解析计算。

| 指标 | 结果 |
|---|---|
| 平均出 SSR 所需抽数 | **约 36.3 抽** |
| 40 抽内出 SSR 的概率 | 35.8% |
| 50 抽内出 SSR 的概率 | 97.6% |
| 综合 SSR 出率（含保底） | 约 2.75% |
| 综合 SR 出率 | 约 11.75% |
| 综合 R 出率 | 约 25.7% |
| 综合 N 出率 | 约 59.8% |
| 平均出 UP 套装件所需抽数（含大保底） | 约 54.5 抽 |

> 公示页展示“基础概率 + 保底规则”，同时展示“当前保底计数”。
> 开发时在服务端写一个独立的**概率模拟命令**（`tools/gacha_sim`），跑 10 万次并与上表对比，作为自测项。

**参考模拟代码（逻辑）**

```python
def ssr_rate(n):          # n = 距上次 SSR 的第几抽（从 1 起）
    if n >= 60: return 1.0
    if n >= 40: return min(1.0, 0.01 + 0.04 * (n - 39))
    return 0.01
```

### 13.7 版本与热更

- 配置文件（JSON）作为 `config` 资源包的一部分发布；`config_version`（整数）在导出内容哈希变化时自动 +1。
- 登录时客户端上报 `config_version`，服务端不一致则要求更新（见 `05_协议与接口.md`）。
- 新增字段 / 新增表属于 `Game.Config` 热更程序集变更；活动类内容（新卡池）只增数据行与资源包。
